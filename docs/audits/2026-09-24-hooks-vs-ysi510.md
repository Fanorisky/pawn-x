## 0. HEADLINE VERDICT

**The old "symmetric non-gap" claim is FALSE against YSI 5.10.**

Prior claim (from exp 004/005/007, based on a v4-era tree): *"native-hooking a real
function/native is a symmetric non-gap: YSI's `@Hy_native` path is vestigial."*

YSI 5.10 genuinely hooks **real functions and natives** via `hook function` /
`hook native` / `hook stock`, and it is neither vestigial nor unimplemented. It is
**implemented and unit-tested** (`y_hooks_tests.inc`: 3 `hook native` + 3 `hook stock`
cases, with `continue()` chaining, `numargs`, varargs forwarding, `DEFINE_HOOK_RETURN__`).

The mechanism is real call-site redirection, not callback dispatch:
`public OnCodeInit()` (`y_hooks_impl.inc:1302`) walks the **entire code segment**
(`for (new addr = AMX_HEADER_COD; addr < 0;)`, line 1562/1657) and rewrites **every**
`SYSREQ.C` / `SYSREQ.D` / `SYSREQ.N` (native invocations) and `OP_CALL` (pawn
function/stock invocations) whose target matches a hooked symbol, replacing the target
with the hook trampoline (`AMX_Write(addr, _:call)` / `AMX_Write(addr + __1_cell, idx)`,
lines 1602-1652). Result: *every* call to e.g. `SetPlayerPos(...)` anywhere in the
script is intercepted, and `continue(...)` invokes the next hook or the original.

**pawn-x has NO equivalent to this**, in either pillar:

- The **compiler `hook`** (`sc1.c:2337 hook_emit_dispatchers`) only synthesises a
  `public Name(args)` **dispatcher**: it hooks things that are *dispatched by name*
  (callbacks/publics). It never touches internal `SYSREQ`/`CALL` call sites. `dohook()`
  (`sc1.c:2124`) parses only `hook default`, `hook:N`, `hook <state>`, and a bare
  callback name. There is **no `function` / `native` / `stock` keyword at all**.
- The **`dynhook` plugin** (`experiments/006-companion-plugin/dynhook.cpp`) inline-hooks
  `amx_Exec` (`Exec_hook`, line 228), i.e. it intercepts **public/callback dispatch by
  index**, not internal native (`SYSREQ`) or function (`CALL`) invocations. Confirmed:
  it maps `index → public name` and only acts on the public-dispatch path.

**The real gap (one sentence):** pawn-x cannot intercept an ordinary in-script call to a
native or pawn function (`SetPlayerPos(...)`, `random(...)`, `printf(...)`) and route it
(with explicit `continue`-based chaining) through user hooks; it can only chain
*callbacks* (things the host or the script dispatches by name).

## 2. What pawn-x actually ships (verified)

**Pillar 1: compiler `hook` (`sc1.c`, `hook.inc`)**, callback-level only:
- `dohook()` (`sc1.c:2124`): each `hook Name(args) body` becomes a hidden
  `_hook.Name.<seq>` function; `hook_register` records it.
- `hook_emit_dispatchers()` (`sc1.c:2337`): emits one `public Name(args)` that calls each
  hidden body **in priority-then-source order** (insertion sort, `sc1.c:2355`), forwarding
  args by slot (`push.s`, line 2404), applying return control:
  `HOOK_STOP`(-1)→return 0, `HOOK_STOP_1`(-2)→return 1, `HOOK_CONTINUE`(1)/`HOOK_CONTINUE_0`(0)
  set the running chain value; fall-through returns the declared `hook default` or the last
  chain value (`sc1.c:2415-2446`).
- Extras: `hook default Name = k;` (`dohook`, line 2140 → `hook_set_default`), `hook:N`
  priority (line 2168), `hook <state>` / `hook <automaton:state>` gating (line 2188, emitted
  as a runtime state compare + skip, `sc1.c:2396-2402`).
- Reserves `hook` as a **keyword** and hard-errors if YSI `y_hooks` is also included
  (`hook.inc:8-10`); the two cannot coexist in one unit.

**Pillar 2: `dynhook` companion plugin (`dynhook.cpp`, `dynhook.inc`)**, callback-level only:
- Runtime registry `map<string, vector<string>>`; natives `dynhook_add/remove/replace/
  clear/count/call` + `dynhook_intercept`.
- Phase B transparently intercepts a **public callback** by inline-hooking `amx_Exec`
  (`Exec_hook`, `dynhook.cpp:228`), mapping call `index → public name`
  (`g_pubNames`), running the runtime chain as a PRE-hook with the same
  `HOOK_CONTINUE/STOP/STOP_1` control, then the original. Cancel (`HOOK_STOP`) emulates
  amx_Exec's stack cleanup by hand.
- This adds a capability YSI lacks: **true runtime add/remove/replace** of callback
  handlers (chain grows/shrinks 0↔N live). But it operates on the *public dispatch*
  boundary; it does **not** see internal `SYSREQ`/`CALL` sites.

## 4. The real NEW gaps (most significant first) + how hard to close

### Gap A. `hook native` / `hook function` / `hook stock`: real call-site interception  (matrix #8)
The genuine new YSI 5.10 capability. Intercept every in-script call to a named native or
pawn function and route it through user hooks. **pawn-x has nothing.**

- **Compiler-closable? YES, and pawn-x is in a *better* position than YSI.**
  YSI must do fragile *runtime* code-segment rewriting (scan `SYSREQ`/`CALL`, patch
  addresses at `OnCodeInit`) precisely because it is only an include and cannot change how
  calls are emitted. pawn-x *is* the compiler: it can, at compile time, rename the original
  symbol, emit a wrapper under the real name, and resolve the hook's `continue`/original-call
  to the renamed original: clean, deterministic, JIT-safe, zero startup scan. This is the
  same architecture already used for the `hook` dispatcher and the `yield` generator
  rewrite, extended to call redirection.
- **Difficulty: MEDIUM.** Needs (1) a `hook function|native|stock Name(args)` parse path in
  `dohook()`, (2) a compile-time call-redirection pass (native `SYSREQ` and pawn `CALL`
  sites → wrapper), and (3) a `continue(...)` intrinsic that calls the next-in-chain /
  original with forwarded (incl. vararg) args. Natives are the easier half (compiler owns
  `SYSREQ` emission); pawn functions need the redirection to also cover already-emitted
  intra-unit calls. Cross-`.amx` interception is out of scope (as before).
- **Plugin-only fallback?** Partial and worse: a plugin could subhook the native table to
  intercept *natives* process-wide, but internal pawn-function `CALL`s are not visible at a
  clean boundary, and per-script targeting is awkward. The compiler is the right pillar.

### Gap B: `continue`-based explicit chaining  (matrix #9)
Even for the callback case, YSI hooks can call `continue(...)` to run the rest of the chain
at a chosen point, wrap it (pre/post), call it multiple times, and return arbitrary values.
pawn-x's dispatcher is a fixed forward walk with only STOP/CONTINUE control.

- **Compiler-closable? YES.** Reuse the same `continue`-intrinsic + trampoline needed for
  Gap A; the dispatcher would pass a "resume point / next index" so a body can invoke the
  remainder explicitly. **Difficulty: MEDIUM**, largely shared with Gap A (do them together).

### Gap C: ALS-equivalence / declared-order interleaving with `#define` hooks  (matrix #10)
Purely a consequence of Gap A. Once function hooks exist, matching YSI's "function hooks and
ALS `#define` hooks interleave in source order" is mostly ordering bookkeeping.
- **Compiler-closable? YES, LOW-MEDIUM**, but only meaningful after Gap A.

### Gap D: varargs / `numargs` fidelity inside hooks  (matrix #11)
For callback hooks pawn-x forwards fixed args only; `continue`-forwarding of `...`/`___`
and `numargs()` semantics inside a hook body are unverified/absent.
- **Compiler-closable? YES, MEDIUM** (ties into y_va `___` mirror + the `continue` intrinsic).

### (Non-gap) Coexistence with YSI keywords  (matrix #13)
pawn-x deliberately can't co-include YSI y_hooks. If a user wants YSI's function hooks *and*
pawn-x, today they must choose. Not a capability gap per the north-star ("standalone
replacement"), but worth stating honestly: until Gap A closes, a script that needs
`hook native` must use YSI, and then cannot use pawn-x's `hook`.

## 5. Prior pawn-x claims that were true vs YSI-4 but are now WRONG vs YSI 5.10

1. **"native-hooking a real function/native is a symmetric non-gap; YSI's `@Hy_native`
   path is vestigial."**: **NOW FALSE.** YSI 5.10 fully implements and tests
   `hook native`/`hook stock` (and `hook function` as a synonym) with real call-site
   rewriting. This is the central correction.

2. **exp 005 RESULT.md:** *"Runtime hook add/remove/replace … is the ONLY real capability
   gap … Everything a compiler can own is covered."*: **NOW FALSE / incomplete.** The
   parity test only exercised *original callback* hooks ("two hooks on the real
   `OnGameModeInit`") and even ran the YSI side with `PAWN_X_NO_YSI_ITERATORS` and legacy
   include hacks. It never exercised `hook native`/`hook function`, so it missed the biggest
   compiler-ownable capability YSI 5.10 has. "Everything a compiler can own is covered" is
   wrong: function/native call-site interception is compiler-ownable and is NOT covered.

3. **exp 005 RESULT.md point 4:** *"YSI's `hook` only *intercepts* an existing public, so
   the target must be `forward`ed…"*: **NOW FALSE as a general statement.** True of the
   *original* `hook` only; YSI 5.10 also hooks natives and pawn functions, not just publics.

4. **exp 004 RESULT.md "Where YSI still wins":** lists only (1) runtime add/remove/replace
   and (2) cross-`.amx` chain control as YSI's edge. **INCOMPLETE.** Misses
   `hook function`/`hook native`/`hook stock` entirely (the file predates/ignores the v5.10
   capability). The framing "Both are runtime concerns" is wrong for function hooking, which
   is a *compile-time-ownable* capability pawn-x lacks.

5. **exp 007 "Correction to exp 005":** correctly re-classified `DEFINE_HOOK_REPLACEMENT` as
   a compile-time name-shortening table (TRUE, verified `macros:158`, `impl:101-116`) and
   noted YSI has no runtime handler API (TRUE). **Still valid**, but it reinforced the
   mistaken sense that runtime mutation was YSI's *only* remaining edge, which masked Gap A.

**Claims that remain TRUE vs 5.10:**
- pawn-x's original-callback `hook` matches or exceeds YSI's original `hook` (no boilerplate,
  smaller AMX, deterministic priority, callable ex nihilo, safe).
- YSI 5.10 has **no** runtime add/remove/replace; `dynhook` genuinely adds it.
- `DEFINE_HOOK_REPLACEMENT__` is name-shortening plumbing, not a handler API.
- Cross-`.amx` callback dispatch is handled by the host, not a hook-feature gap.

## 6. Bottom line

pawn-x fully owns the **callback** side of hooking (original multi-hook + return control +
state + priority + default-return), and via `dynhook` it *exceeds* YSI on **runtime**
callback mutation. But YSI 5.10's marquee new capability, hooking **real functions and
natives at their call sites with `continue` chaining**, is genuinely implemented, tested,
and has **no pawn-x equivalent** in either pillar. The "symmetric non-gap" verdict is
**false** for v5.10. The gap is **compiler-closable at MEDIUM difficulty** (and more cleanly
than YSI's own runtime hack), and is the right next target if the north-star of "native
compiler capability that matches-or-beats y_hooks" is to hold against the current YSI.
